# 全员通用 Git 协同底线

作为 Trae 工作区内的 AI 助手，当你协助用户执行 Git 操作时，必须将以下规则视为最高物理指令：

## 👁️ 前置状态感知 (Read-Before-Write)
- **强制真实环境核对**：在执行任何 Git 写入操作（`add`、`commit`、`push`）或分支变更操作（`checkout`、`merge`）之前，**你必须主动静默执行终端命令**（如 `git branch --show-current` 和 `git status`），以获取当前真实的物理分支状态。
- **反幻觉声明**：绝对禁止基于对话历史、上下文猜测或假设当前所处的分支！一切操作的基准必须以终端真实的输出结果为准。

## 🚨 绝对红线 
- **禁止直推生产主干**：绝对禁止在 `master` 或 `main` 生产主干分支上直接执行 `commit` 和 `push`。所有发布到生产环境的代码修改必须切出独立的工作分支。**允许在 `develop` 主分支上执行 `commit` 和 `push` 操作（用于日常开发集成）**。
- **禁止内容污染 (Diff 审查)**：执行 `git add` 前，必须静默检查 `git diff` 的具体变更内容。
  1. **拦截代码残留**：重点拦截业务代码中的 `console.log`、`var_dump`、`debugger` 等调试残留代码，以及显而易见的测试硬编码。
  2. **最后防线兜底**：确保 `.env`、秘钥、数据库配置等敏感文件未因 `.gitignore` 配置失效而被误追踪。发现上述污染必须立刻拒绝提交，并提示用户清理。
- **禁止盲目描述**：绝对拒绝生成诸如 `update`、`fix bug`、`modified` 这种毫无溯源和追踪价值的 Commit Message。

## 🚀 MR 自动创建流程 (GitLab Push Options)
当用户要求"提交 MR"、"发起合并请求"、"创建 PR" 或在推送时明确表达合并意图时，必须使用 GitLab Push Options 自动创建 MR：

### 触发条件
**仅当用户明确提出 MR 意图时触发**：
- 用户明确说"提交 MR"、"创建合并请求"、"发起 PR"
- 用户在推送时说"帮我创建 MR"、"推送并创建 MR"

**注意**：普通提交（"提交代码"、"推送代码"）不触发 MR 创建，仅执行 `git push`。

### 执行流程
1. **确认分支状态**：静默执行 `git branch --show-current` 确认当前分支（必须非 `master` 或 `main` 生产主干分支）
2. **生成 MR 标题**：根据角色专属 Commit 规范生成，格式参考角色护栏文件
3. **执行 Push Options**：
   ```bash
   git push -o merge_request.create \
            -o merge_request.target=master \
            -o merge_request.title="<MR标题>" \
            -o merge_request.remove_source_branch \
            origin <当前分支名>
   ```
4. **降级策略**：若 Push Options 失败，自动降级为普通推送并提示用户手动创建 MR

### MR 标题生成规则
- **优先使用角色专属模板**：若角色护栏定义了 MR 标题格式，严格遵循
- **默认格式**：`<类型>: <描述>`（类型参考角色 Commit 规范）
- **示例**：`[文档](用户系统): 新增 v2.0 用户权限模块 PRD`

### MR 描述模板
MR 描述内容由角色护栏定义，若未定义则使用通用模板：
- **变更概述**：简要说明本次变更的目的和内容
- **影响范围**：列出受影响的模块或文件
- **测试情况**：说明验证方式（如适用）

## 🚦 格式与规范授权 (动态约束)
由于本工作区包含产品、测试与不同语言的研发人员，且各自挂钩不同的项目管理系统：
- **严禁擅自决定格式**：你不可以自作主张使用任何默认的分支命名规范或 Commit 格式（包括但不限于常规的 Angular 规范）。
- **严格遵循角色契约**：具体的分支命名规则、Commit 格式（如 TAPD/Jira 任务 ID 追踪）以及 Merge Request (MR) 的提交流程，以**运行时注入的角色专属护栏文件为准**。若角色护栏未定义相关规范，则仅执行本通用底线。
