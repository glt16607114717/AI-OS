## 一、三层模型定义

### 1.1 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│                       用户自然语言指令                          │
│                  "修个bug" / "建张表" / "提MR"                 │
└──────────────┬───────────────────────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────────┐
│                    第一层：规则 (Rules)                         │
│                                                              │
│  职责：意图感知 → 上下文约束 → 技能路由                          │
│  特征：被动触发，不执行任何操作，只声明"该怎么做"                   │
│  载体：.trae/rules/*.md                                      │
└──────────────┬───────────────────────────────────────────────┘
               │ 路由指令
               ▼
┌──────────────────────────────────────────────────────────────┐
│                    第二层：技能 (Skills)                        │
│                                                              │
│  职责：封装可执行能力，编排具体操作步骤                            │
│  特征：主动执行，内部决定是否调用 MCP                             │
│  载体：.trae/skills/*/SKILL.md                                │
└──────────────┬───────────────────────────────────────────────┘
               │ 按需调用
               ▼
┌──────────────────────────────────────────────────────────────┐
│                    第三层：MCP (外部服务)                       │
│                                                              │
│  职责：对接外部系统，提供工具化接口                               │
│  特征：纯工具层，无业务逻辑                                      │
│  载体：.trae/mcp.json (配置) + 远程服务                        │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 三层职责对比

| 维度 | 规则 (Rules) | 技能 (Skills) | MCP (外部服务) |
|------|-------------|---------------|---------------|
| **核心职责** | 感知意图、提供约束、路由技能 | 封装可执行能力、编排步骤 | 对接外部系统、提供工具接口 |
| **触发方式** | 由 IDE 引擎自动匹配触发 | 由规则路由或用户直接调用 | 由技能内部按需调用 |
| **是否执行操作** | ❌ 只声明不执行 | ✅ 执行具体操作 | ✅ 执行远程调用 |
| **是否有状态** | 无状态（纯文本声明） | 无状态（每次独立执行） | 有状态（连接、认证、会话） |
| **谁调用谁** | 被IDE引擎加载 → 路由到技能 | 被规则路由 → 调用MCP | 被技能调用 |
| **可否独立使用** | 可独立（纯约束型规则） | 可独立（简单技能不依赖MCP） | 不可独立（必须由技能封装） |

### 1.3 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **规则触发技能，技能调用 MCP** | 用户不直接调用技能，技能不直接暴露 MCP。三层各司其职 |
| 2 | **一条规则只做一件事** | 规则的职责必须单一：要么提供约束、要么路由流程、要么定义规范。禁止混合 |
| 3 | **技能可独立于 MCP** | 简单技能（如 git-commit、打断点）不需要 MCP，这是正常的 |
| 4 | **规则必须声明触发时机** | 每条规则的 frontmatter 必须明确 `description` 字段，描述何时触发 |
| 5 | **规则必须声明技能路由** | 凡是涉及操作执行的规则，必须在正文中明确"调用技能 X" |

## 二、规则层架构

### 2.1 规则分类模型

按职责性质，规则分为三类：

```
规则 (Rules)
├── 常识型规则 (Knowledge)     — 提供静态知识，不路由技能，alwaysApply=true
├── 约束型规则 (Constraint)    — 提供行为护栏，不路由技能，alwaysApply=false
└── 流程型规则 (Workflow)      — 编排操作步骤，路由技能，alwaysApply=false
```

| 类型 | 触发方式 | 是否路由技能 | 典型内容 |
|------|---------|:----------:|---------|
| **常识型** | 每次对话自动加载 | ❌ | 个人身份、项目架构、环境配置表 |
| **约束型** | 关键词条件触发 | ❌ | 编码规范、命名规范、Git红线、环境红线 |
| **流程型** | 关键词条件触发 | ✅ | Bug修复流程、任务开发流程、数据库设计流程 |

### 2.2 规则命名规范

**格式**: `{岗位标识}-{功能描述}.md`

| 前缀 | 适用范围 | 说明 |
|------|---------|------|
| `common-` | 跨岗位通用 | 所有角色共享的规则 |
| `backend-php-` | 后端PHP开发 | 脚手架定义的 `rmp_platform/backend-php` 岗位 |
| `frontend-vue-` | 前端Vue开发 | 脚手架定义的 `rmp_platform/frontend-vue` 岗位 |
| `qa-` | 测试工程师 | 脚手架定义的 `rmp_platform/qa` 岗位 |
| `pm-` | 产品经理 | 脚手架定义的 `rmp_platform/pm` 岗位 |

> 岗位标识来源于脚手架 `ai_program/2_departments/{部门}/roles/{角色}/role.yaml` 中的 `name` 字段。

### 2.3 规则文件标准结构

```yaml
---
alwaysApply: true|false
description: "触发条件：当用户要求XXX、说XXX、或涉及XXX时触发。"
---

# 规则标题

## 触发时机
[明确描述什么场景、什么关键词会触发本规则]

## 技能路由
[仅流程型规则需要此节]
- 当涉及XXX时 → 调用技能 `skill-name`
- 当需要XXX时 → 调用技能 `skill-name`

## 规则内容
[具体的约束、规范、流程步骤]
```

## 三、技能层架构

### 3.1 技能分类模型

```
技能 (Skills)
├── 业务流程型    — 编排多步骤业务流程，通常依赖多个 MCP
├── 工具封装型    — 封装单一工具能力，可能依赖 0~1 个 MCP
├── 纯本地型     — 完全不依赖外部服务，纯本地操作
└── 元技能型     — 用于管理其他技能或配置的技能
```

## 四、MCP 层架构

### 4.1 MCP 服务全景

| MCP 服务 | 提供的工具 | 典型消费者（技能） | 典型场景 |
|----------|----------|-----------------|---------|
| `mcp-server-tapd` | get_bug, update_bug, create_bug, get_stories_or_tasks, update_story_or_task, create_story_or_task, create_comments, get_comments, get_workflows_all_transitions, get_entity_custom_fields, get_entity_attachments, get_image, send_qiwei_message | `rmp-tapd`, `tapd` | 项目管理、需求/任务/Bug 操作 |
| `mcp-nnd` (mysql_execute) | mysql_execute | `php-api-debug`, `mysql-designer`, `api-doc-generator` | 数据库查询、数据验证、表结构分析 |
| `mcp-nnd` (mongo_execute) | mongo_execute | `查询接口日志` | 接口请求日志查询 |
| `mcp-apipost` | get_project_tree, search_target, get_target_detail, import_swagger, delete_targets, search_model, create_target, create_project, get_env_details, get_global_param_details | `apipost-sync` | 接口文档同步到 Apipost |

### 4.2 MCP 调用约束

| # | 约束 | 说明 |
|---|------|------|
| 1 | **禁止直接调用 MCP** | 用户指令不直接路由到 MCP，必须经过技能封装 |
| 2 | **一个技能可以调用多个 MCP** | 如 `php-api-debug` 同时可能调用 `mcp-nnd_mysql_execute` |
| 3 | **MCP 不包含业务逻辑** | MCP 只提供原子化工具，业务编排由技能完成 |
| 4 | **环境隔离** | MCP 调用必须指定环境（dev/test/gray/prod），由规则层约束权限 |

### 4.3 MCP → 技能 → 规则 的反向依赖图

```
mcp-server-tapd
  ├── rmp-tapd (技能)
  │     └── backend-php-bug-flow (规则)
  └── tapd (技能)
        └── backend-php-task-flow (规则)

mcp-nnd_mysql_execute
  ├── php-api-debug (技能)
  │     ├── backend-php-bug-flow (规则)
  │     └── backend-php-task-flow (规则)
  ├── mysql-designer (技能)
  │     └── common-env-mysql / backend-php-mysql (规则)
  └── api-doc-generator (技能)
        └── (无规则路由，IDE直触)

mcp-nnd_mongo_execute
  └── 查询接口日志 (技能)
        └── backend-php-bug-flow (规则)

mcp-apipost
  └── apipost-sync (技能)
        └── (无规则路由，IDE直触)
```

## 五、联动机制设计

### 5.1 完整联动链路（以 Bug 修复为例）

```
用户说: "修个bug"
         │
         ▼
    ┌─────────────────────────────────────────────┐
    │ IDE 引擎扫描所有规则的 description 字段       │
    │ 匹配到: backend-php-bug-flow.md              │
    │   description: "当用户说修bug、改bug..."      │
    └────────────────┬────────────────────────────┘
                     │ 规则被加载
                     ▼
    ┌─────────────────────────────────────────────┐
    │ 规则内容生效，提供:                           │
    │  1. 流程步骤约束（mermaid流程图）              │
    │  2. 技能路由声明（第X步调用技能Y）             │
    │  3. MCP工具清单（技能内部调用的MCP列表）        │
    └────────────────┬────────────────────────────┘
                     │ 按流程路由
                     ▼
    ┌─────────────────────────────────────────────┐
    │ Step 1: 调用技能 rmp-tapd                     │
    │   └→ 内部调用 mcp-server-tapd.get_bug         │
    │ Step 2: 调用技能 查询接口日志                   │
    │   └→ 内部调用 mcp-nnd_mongo_execute           │
    │ Step 3: 调用技能 打断点                        │
    │   └→ 纯本地操作，不调用MCP                     │
    │ Step 4: 调用技能 php-api-debug                 │
    │   └→ 内部调用 mcp-nnd_mysql_execute           │
    │ Step 5: 调用技能 git-commit                    │
    │   └→ 纯本地操作，不调用MCP                     │
    │ Step 6: 调用 mcp-server-tapd.update_bug       │
    │ Step 7: 调用 mcp-server-tapd.create_comments  │
    └─────────────────────────────────────────────┘
```

### 5.2 简单联动链路（以建表为例）

```
用户说: "建一张客户表"
         │
         ▼
    ┌─────────────────────────────────────────────┐
    │ IDE 引擎匹配到: common-env-mysql.md          │
    │   description: "数据库设计、建表、字段设计..." │
    └────────────────┬────────────────────────────┘
                     │ 同时匹配
                     ▼
    ┌─────────────────────────────────────────────┐
    │ IDE 引擎匹配到: backend-php-mysql.md         │
    │   description: "MySQL设计规范、索引设计..."    │
    └────────────────┬────────────────────────────┘
                     │ 两条规则同时生效
                     ▼
    ┌─────────────────────────────────────────────┐
    │ 路由到技能: mysql-designer                    │
    │   └→ 内部调用 mcp-nnd_mysql_execute          │
    │       (查询现有表结构作为参考)                  │
    │   └→ 生成 Migration 文件                      │
    └─────────────────────────────────────────────┘
```

### 5.4 孤岛技能（无规则路由的技能）

以下技能目前**没有被任何规则路由**，依赖 IDE 引擎直接通过技能自身的 description 触发：

| 技能 | 原因 | 建议 |
|------|------|------|
| `api-doc-generator` | 属于低频工具型，无对应流程规则 | 可保持现状，或创建 `backend-php-doc-flow` 规则 |
| `apipost-sync` | 属于低频工具型，无对应流程规则 | 可保持现状 |
| `create-model` | 属于低频工具型，无对应流程规则 | 可保持现状，或合并入 `backend-php-mysql` 规则路由 |
| `structured-debugger` | 属于独立调试工具，有独立触发词 | 可保持现状 |
| `domain-code-reviewer` | 属于独立审查工具，有独立触发词 | 可保持现状 |
| `adr-generator` | 属于独立文档工具，有独立触发词 | 可保持现状 |
| `docsify-preview` | 属于独立文档工具，有独立触发词 | 可保持现状 |

> **设计决策**: 不是所有技能都需要被规则路由。低频、独立的工具型技能可以直接通过 IDE 引擎匹配其 description 触发。规则路由主要服务于**有明确流程步骤的复杂业务场景**（如 bug 修复、任务开发、数据库设计）。

## 六、命名规范体系

### 6.1 规则命名

```
{岗位标识}-{功能描述}.md

示例:
  common-personal.md          # 通用：个人身份与基本规范
  common-git-workflow.md      # 通用：Git协作底线
  common-env-mysql.md         # 通用：MySQL查询规约
  php-coding.md       # PHP后端：编码规范
  backend-php-bug-flow.md     # PHP后端：Bug修复流程
  backend-php-task-flow.md    # PHP后端：任务开发流程
  frontend-vue-coding.md      # Vue前端：编码规范（未来扩展）
```

### 6.2 技能命名

技能命名保持现有风格（小写英文或中文），不做强制变更。原因：
- 技能由 IDE 引擎通过 description 触发，文件名对用户不可见
- 技能名在规则中以反引号引用（如 `mysql-designer`），可读性已足够

### 6.3 MCP 命名

MCP 服务名在 `mcp.json` 中定义，保持现有命名不变：
- `mcp-server-tapd`
- `mcp-nnd`（提供 mysql_execute 和 mongo_execute）
- `mcp-apipost`

## 八、演进方向

### 8.1 当前阶段（v1.0 现状）

- 规则 13 条，命名无章法，存在 2 处职责重叠
- 技能 18 个，与规则的路由关系不完整（约 40% 的技能无规则路由）
- MCP 4 个服务，调用链路基本清晰

### 8.2 下一阶段（v2.0 目标）

| 维度 | 目标 | 具体动作 |
|------|------|---------|
| **命名规范化** | 所有规则加岗位前缀 | 批量重命名 13 条规则 |
| **消除重叠** | 解决 P1~P4 问题 | 合并重叠规则，拆分混合规则 |
| **路由补全** | 关键技能都有规则路由 | 为 `create-model` 等补充路由声明 |
| **结构统一** | 所有规则遵循标准结构 | 补齐缺失的"触发时机"和"技能路由"章节 |

### 8.3 远期阶段（v3.0 展望）

| 维度 | 展望 |
|------|------|
| **多岗位扩展** | 当 `frontend-vue`、`qa` 等角色开始使用时，按 `{岗位}-` 前缀自动隔离规则 |
| **技能市场** | 技能可跨岗位共享，但规则按岗位隔离 |
| **规则版本化** | 规则纳入 Git 管理，通过 `nnd-trae-sync` 技能实现团队级同步 |
| **MCP 动态注册** | MCP 服务通过配置中心动态管理，不再手动编辑 `mcp.json` |

## 九、架构原则速查表

| # | 原则 | 一句话说明 |
|---|------|----------|
| 1 | 规则触发技能 | 用户不直接调技能，由规则路由 |
| 2 | 技能调用 MCP | MCP 不直接暴露给用户 |
| 3 | 一规则一事 | 混合型规则必须拆分 |
| 4 | 岗位前缀 | 文件名即适用范围 |
| 5 | 声明触发时机 | description 必填 |
| 6 | 声明技能路由 | 流程型规则必填 |
| 7 | 技能可无 MCP | 简单技能不需要外部依赖 |
| 8 | 孤岛技能可接受 | 不是所有技能都需要规则路由 |
