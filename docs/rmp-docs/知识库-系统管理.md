## 1. 系统与权限

本业务域是整个 RMP 系统的安全基石，包含认证登录、RBAC 权限模型、用户管理、角色管理、菜单管理五大子模块。核心设计原则：**多租户隔离 + 四级数据范围 + 权限组树形授权**。

### 1.1 认证登录（AuthController）

#### 模块职责
- 登录验证（密码/企业微信/微信/小程序四种身份类型）
- 登录前判断是否需要验证码
- 注销登出（JWT 黑名单机制）
- 离职审批状态回调（企业微信审批系统集成）

#### 核心逻辑

**多身份登录**：`identity_type` 支持 4 种类型（`UserAuth::IDENTITY_TYPE_LIST`）：
- `0` 用户名密码（username）
- `1` 企业微信（work_wechat）
- `2` 微信（wechat）
- `4` 小程序（miniprogram）

**验证码触发机制**：登录失败次数达到阈值后触发验证码，err_code `1102/1103/1203` 表示验证码校验失败。

**登录日志全链路**：通过 `LoginLogService::upsert()` 记录每次登录尝试，包含 account、fingerprint、ip、user_agent、login_method、verify_triggered、verify_result、fingerprint_trusted 等字段。

#### 关键 API
| 方法 | 路由 | 用途 |
|------|------|------|
| GET | `/api/admin/check-login-need-verify` | 检查是否需要验证码 |
| POST | `/api/admin/login` | 登录 |
| POST | `/api/admin/rbac/logout` | 注销 |

### 1.2 RBAC 权限模型（RbacController）

#### RBAC 架构详解

RMP 采用 **ThinkRbac** 库实现权限控制，核心关系链：

```
用户(User) → 角色(Role) → 角色权限组(RolePermissionGroup) → 权限组(PermissionGroup) → 权限(Permission)
```

**多租户支持**：每个角色通过 `company_id` 实现租户隔离，权限组通过 `permission_platform` 区分 PC 端和上位机(IPC)端权限。

**四级数据范围**（`Role::DATA_RANGE_LIST`）：
- 全部数据
- 本公司数据
- 本部门数据
- 个人数据

数据范围通过 `AdminAuth` 中间件在查询时自动注入条件。

**权限组树形结构**：权限组通过 `pid`（父级 ID）构建树形菜单/按钮权限体系，字段包括：
- `type`：1=页面路由，2=按钮，3=其他
- `behavior`：page/add/edit/show/delete/other
- `permission_platform`：PC/IPC（逗号分隔多平台）
- `code`：唯一标识（alphaDash，如 `customer_list`）
- `cache`：是否缓存权限

**IPC 上位机同步**：`diffPermissionGroup` 支持 `type=ipc` 将权限单独同步给上位机，通过 `DbCache` 记录更新时间戳，上位机拉取账号时同步角色权限。

### 1.3 用户管理（UserController）

#### 模块职责
- 用户信息聚合查询（基础信息 + 账号 + 角色 + 权限 + 组织 + 公司）
- 密码修改、账号绑定/解绑（微信/企业微信）
- 用户列表、T 下用户、IT 解锁
- 离职数据转移（权限交接）
- 企业微信消息推送

#### 核心逻辑

**用户信息聚合**（`getUserInfo`）：一次性返回用户全量信息，前端登录后初始化使用：
```
user_info + user_account + staff_info + commission_config + role_info + permission_group(树形) + company_info
```

**权限组树构建**：根据用户角色获取权限组后，通过 `array_to_tree()` 构建前端可直接渲染的菜单树。

**流程用户信息**（`getUserInfoForFlow`）：为工作流审批提供精简用户信息，包含 roleList 和 deptInfo。

**离职数据转移**（`dataTransfer` / `departHandOver`）：将离职用户的客户、业务数据转移给交接人，支持企业微信审批回调自动触发。

## 2. 公司/组织架构

本业务域管理企业的多级公司架构、部门层级树和员工（Staff）信息，是 RBAC 数据范围的基础。

### 2.1 公司管理（CompanyController）

#### 模块职责
- 公司层级树管理（总公司 → 子公司，通过 `relation_chain` 实现无限层级）
- 公司 CRUD + 管理员账号管理
- 公司账套设置（核算方式、本位币、期初账期、科目体系）
- 公司统计（稼动率、结算数据、客户分析）

#### 核心逻辑

**公司层级树**：通过 `relation_chain`（逗号分隔的父级ID链）实现多级公司架构。`type=full` 可获取全集团数据，`type=self` 只看本公司。

**核算方式**：
- `1` 独立核算（ACCOUNTING_METHOD_INDEPENDENT）
- `2` 挂靠核算（ACCOUNTING_METHOD_DEPENDENT，挂靠到父公司 `affiliate_company_id`）

**账套管理**：每家公司可配置独立的财务参数：
- `currency`：CNY/USD/HKD
- `initial_period`：期初账期（YYYYMM）
- `account_system`：科目体系（1/2）

## 5. 工作流与审批

工作流是 RMP 的核心业务引擎，包含**新工作流引擎**（WorkFlowController，模板→实例→任务）和**旧流程引擎**（FlowEngineController，对接外部审批系统）两套体系。

### 5.1 新工作流引擎（WorkFlowController）

#### 三层架构：模板 → 实例 → 任务

```
WorkFlow（工作流配置）
  └── WorkFlowTemplate（模板）
        └── WorkFlowTask（任务配置）
              └── WorkFlowTaskFormField（表单字段）
              └── WorkFlowAssignRule（分配规则）
                    └── WorkFlowAssignCondition（条件）
                    └── WorkFlowAssignStrategy（策略）

WorkFlowInstance（工作流实例）
  └── WorkFlowInstanceTemplate（实例-模板关联）
  └── WorkFlowPendingTask（待分配任务）
```

#### 核心概念

**工作流（WorkFlow）**：业务流程的顶层定义，绑定一组模板。
- `work_flow_code`：编码（如 `purchase_flow`）
- `business_type`：业务类型
- `company_type`：公司类型
- `status`：启用/停用

**模板（Template）**：工作流中的一个阶段定义，包含多个任务。
- `template_code`：编码
- `version`：版本号（任务变更时自增）
- `task_ids`：包含的任务ID列表

**任务（Task）**：流程中的具体节点。
- `task_type`：审批任务(TYPE_APPROVE) / 执行任务(TYPE_EXECUTE)
- `condition_field`：条件字段（审批状态/任务结果）
- `condition_value`：条件值（通过/驳回/完成/失败）
- `default_action`：默认动作
- `pre_task_id`：前置任务
- `form_fields`：表单字段配置（JSON）

**分配规则（AssignRule）**：任务自动分配规则。
- `business_module`：业务模块
- `trigger_event`：触发事件
- `dedup_strategy`：去重策略
- `fallback_action`：兜底动作
- `conditions`：分配条件（JSON）
- `strategy`：分配策略

**表单字段类型**（WorkFlowTaskFormField::FIELD_TYPE_MAP）：支持多种字段类型，每个字段可配置权限（PERMISSION_MAP）和必填（REQUIRED_MAP）。

#### 任务流转逻辑

**审批任务条件**：
- `CONDITION_FIELD_APPROVE_STATUS` + `CONDITION_VALUE_APPROVE_PASS`/`REJECT`

**执行任务条件**：
- `CONDITION_FIELD_TASK_RESULT` + `CONDITION_VALUE_COMPLETED`/`FAILED`

**待分配任务**（PendingTask）：系统自动或手动分配处理人。
- 手动分配：`manualAssignTask`
- 重新分配：`reAssignTask`
- 批量分配：`batchAssignTask`
- 取消分配：`cancelAssignTask`

#### 系统日志

`WorkFlowRepository::writeSysLog()` 将所有工作流操作写入 `r_work_flow_sys_log`，包含操作描述、参数、操作路径、操作人。

### 5.2 旧流程引擎（FlowEngineController）

#### 模块职责
对接外部审批系统（如钉钉/企业微信审批），实现单据审批流转。

#### 审批按钮逻辑

`getExamineInfo` 根据单据状态动态返回可用按钮：

| 按钮 | 条件 |
|------|------|
| submit | 草稿状态 + 流程ID为空 + 操作人是创建者 |
| back | 有流程ID + 非完成状态 + 操作人是发起人/管理员 |
| reSubmit | 草稿状态 + 流程ID不为空 + 有正常任务 |
| examine | 有正常任务 + 非重新提交 |
| submitTask | 任务类型为非审批任务 |
| abnormalExamine | 有异常任务 |
| viewExamine | 有流程ID + 无审批按钮 |
| deApproval | 已完成 + 支持反审核 + 操作人权限 |
| discard | 草稿状态 + 支持作废 |

#### 部门负责人查找逻辑

提交审批时，系统会自动查找部门负责人作为审批人：
1. 优先取 `department.director_id`
2. 若无负责人，取提交人的 `superior_id`（直属上级）
3. 若也无，沿 `relation_chain` 向上查找有负责人的部门

## 附录：RBAC 权限校验流程

```
1. 用户登录 → JWT Token 签发
2. 请求到达 → AdminAuth 中间件解析 Token
3. 获取用户角色（AdminAuth::role()）
4. 根据角色 data_range 注入数据范围条件：
   - 全部：不加条件
   - 本公司：company_id = 当前公司
   - 本部门：department_id IN (本部门及子部门)
   - 个人：creator_user_id = 当前用户
5. 权限校验：
   - 菜单权限：permission_group 树过滤
   - 按钮权限：permissionsCheck(codes) 校验
   - 数据权限：data_range 自动注入
6. IPC 上位机权限：通过 permission_platform='IPC' 单独控制
```

## 附录：工作流任务版本控制

当任务的表单字段或分配规则变更时，任务 `version` 自增：
- 已有实例继续使用旧版本任务
- 新实例使用新版本任务
- `versionChanged` 标识告知前端是否触发了版本变更
