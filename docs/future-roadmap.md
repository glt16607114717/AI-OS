## 一、智能模型路由（Task-Aware Routing）

### 问题

当前路由策略（fixed / round_robin）与任务复杂度无关。简单任务（翻译、问答）和复杂任务（多步推理、代码生成）走同一个模型，造成浪费。

### 方案

在请求 LLM 之前插入一层**轻量分类器**，根据任务复杂度自动选模型：

```
用户消息 → 分类器（小模型/规则，<100ms）
  ├─ 简单（闲聊、翻译、格式转换）→ GLM-4-Flash（免费）
  ├─ 中等（代码、分析、SQL）→ GLM-4.7
  └─ 复杂（架构设计、多步推理）→ GLM-5.2
```

### 实现要点

1. **分类器选型**：先用规则引擎（关键词 + 消息长度 + 历史复杂度），后续可换小模型
2. **与现有路由的关系**：分类器在 `GetRouteByStrategy` 之前执行，输出 `complexity` 等级，路由层据此筛选候选模型
3. **兜底**：分类失败或不确定时走默认策略，不影响可用性
4. **可观测**：记录每次分类结果到 `sys_llm_log`，便于分析分类准确率

### 收益

- 成本降低 60%+（大部分对话其实是简单任务）
- 用户无感知，响应更快（小模型延迟更低）

## 二、多智能体协作（Multi-Agent Orchestration）

### 问题

当前是单 Agent 单线程，复杂任务（如"设计权限系统"）需要多轮 tool_calls 逐步推进，缺乏角色分工。

### 方案

在 agentLoop 之上加一层 **Orchestrator**，通过切换 system prompt 实现角色分工：

```
用户: "帮我设计一个用户权限系统"

→ Planner Agent: 拆解任务 → 输出子任务列表
→ DB Agent: 查现有表结构，设计新表
→ Coder Agent: 生成代码
→ Reviewer Agent: 审查安全性
→ 汇总输出
```

### 实现要点

1. **共享上下文**：所有 Agent 共享同一个 messages 数组，通过 system prompt 切换角色
2. **Orchestrator 调度**：Planner 输出子任务 JSON → Orchestrator 逐个分配 → 每个子任务独立 agentLoop
3. **子任务间数据传递**：通过 messages 中的 tool 结果自然传递（前一个 Agent 的产出是后一个的输入）
4. **终止条件**：所有子任务完成 或 总轮数超限

### 待研究

- 编辑器的多 Agent 模式实际体验如何？什么场景下比单 Agent 明显更好？
- Orchestrator 本身是否也需要 LLM 调度，还是用确定性逻辑？

## 三、层级记忆系统（Hierarchical Memory）

### 问题

当前 RAG 是扁平检索（top-5 向量相似度），所有知识同等对待。但实际上：
- 昨天的知识和三个月前的知识价值不同
- 被频繁检索的知识应该更"牢固"
- 长期不用的知识应该被遗忘，避免噪声

### 方案

三层记忆 + 衰减 + 遗忘：

| 层级 | 内容 | 生命周期 | 检索权重 |
|------|------|----------|----------|
| 工作记忆 | 当前对话上下文 | 对话结束清除 | 1.0 |
| 短期记忆 | 近 7 天蒸馏知识 | 每天衰减 ×0.93 | 0.5 ~ 1.0 |
| 长期记忆 | 高频检索、人工标记重要 | 永久 | 0.3 ~ 1.0 |

### 实现要点

1. **衰减机制**：`sys_embedding` 增加 `weight` 字段（0~1），每天凌晨批量衰减短期记忆（×0.93），7 天后降至 0.5 以下
2. **强化机制**：每次被 RAG 检索到且相似度 > 0.7，weight +0.05（上限 1.0）
3. **遗忘机制**：weight < 0.2 且 30 天未被检索 → 标记 `archived=1`，不再参与检索
4. **检索加权**：`final_score = cosine_similarity × weight`，而非纯余弦相似度
5. **人工干预**：Web 界面可手动标记知识为"重要"（weight 直接设为 1.0，永久保留）

### 收益

- 新知识优先被检索（短期记忆权重高）
- 真正重要的知识自然沉淀为长期记忆
- 过时/错误知识自动淘汰

## 四、自进化系统优化（Self-Evolving Enhancement）

### 现状

已有 AI 建议系统（`sys_ai_suggestion`），每天蒸馏时生成建议（rule/skill/bug/tech_vision），人工审核采纳。但做得太粗。

### 优化方向

**4.1 建议质量提升**

- 当前：LLM 一次性生成所有建议，缺乏上下文引用
- 改进：每条建议必须引用**具体对话片段**（对话 ID + 原文摘录），可追溯、可验证
- 增加 `evidence` 字段存储引用证据

**4.2 建议闭环追踪**

- 当前：processed 后无后续
- 改进：采纳后追踪效果（如"规则加强后该问题是否再出现"），形成闭环
- 增加 `adopted_at`、`effect_score` 字段

**4.3 规则违反统计**

- 统计哪些 god_rules 被违反最多 → 自动建议新规则或强化现有规则
- 统计哪些技能被频繁调用但失败 → 自动建议优化技能描述或参数

**4.4 策略效果评估**

- 记录每种路由策略下的用户满意度（对话是否被中断、是否手动切换模型）
- 自动建议策略调整（如"GLM-4.7 在代码类任务中满意度低于 GLM-5.2，建议升级"）

### 核心原则

- **半自动**：AI 提建议，人工审核采纳，不搞全自动（AI 不可靠）
- **可追溯**：每条建议必须有对话证据
- **宁缺毋滥**：不确定的建议不输出

## 五、待探索：业务方终端价值

### 问题

工作台对话（WorkspaceChat）面向不懂技术的业务人员，目前除了数据库查询外，缺乏真正提升效率的场景。

### 已否决的方向

- **自定义工具工坊**：业务方不懂技术，不会自己造工具。正确做法是我们定义技能，他们用。
- **API 开放调用**：业务系统本身有页面，点几下就能完成操作，用 AI 调用接口并没有提升效率。

### 待思考

- 业务方真正高频、重复、痛苦的操作是什么？
- 哪些操作是"页面点很多下"但"一句话就能描述清楚"的？
- 能否从实际业务场景出发，反向定义技能？

## 附录：已否决项及原因

| 方向 | 否决原因 |
|------|----------|
| 自定义工具工坊 | 面向非技术用户，他们不需要也不会造工具 |
| 实时蒸馏 | 单次对话太碎片化，批量蒸馏质量更高 |
| MCP 协议网关 | 已在其他项目实现，非新概念 |
| 知识图谱 | 三元组表达能力有限，复杂信息说不清楚 |
| 语音 Agent 2.0 | 已通过编辑器语音交互实现，无需重复建设 |
